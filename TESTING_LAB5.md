# Лабораторная работа №5 — тестовая модель и автоматизация

## 1. Тестовая модель MVP

### 1.1. Критические пользовательские сценарии

- Регистрация и вход; выход и повторный вход (сессия / cookie).
- Доступ к защищённым маршрутам (редактор, админ-разделы) по ролям.
- Каталог пользовательских материалов: фильтры, сортировка, пагинация.
- Загрузка и выдача файлов (объектное хранилище / presigned URL).
- Публичный прокси погоды: успешный ответ, деградация при недоступности внешнего API или rate limit.
- SEO: `robots.txt`, `sitemap.xml`, метаданные страниц, ответы 410 там, где задано.

### 1.2. Ключевые бизнес-правила и ограничения

- Без валидного токена защищённые API возвращают **401**.
- Операции администратора и пользователя разделены (RBAC); гость не видит админский UI и не проходит на админские маршруты.
- Валидация входных данных (Pydantic / формы): ошибки **422** на API, сообщения на клиенте.
- Лимит запросов к внешнему API погоды на стороне backend; при превышении — контролируемое сообщение без падения приложения.

### 1.3. Зоны повышенного риска

- **Аутентификация и сессии**: истечение токена, повторные запросы с истёкшим cookie.
- **Роли и права**: обход только на клиенте недопустим — проверка на API.
- **Файлы и MinIO**: права на бакет, корректность URL, ошибки сети.
- **Интеграции**: отказ Open-Meteo, таймауты, нестандартный JSON.

## 2. Backend (FastAPI)

| Тип | Каталог | Команда |
|-----|---------|---------|
| Модульные | `backend/tests/unit/` | `pytest tests/unit -m unit` |
| Интеграционные | `backend/tests/integration/` | `pytest tests/integration -m integration` |
| Все | `backend/tests/` | `pytest tests` (в `pytest.ini` включён `-v`: в консоли по строке на каждый тест) |

Окружение: `APP_ENV=test` задаётся в `tests/conftest.py` до импорта приложения; БД — SQLite `:memory:` (см. `config.py`, `database.py`).

Покрытие (пример):

```bash
cd backend
.\venv\Scripts\activate
pytest tests --cov=app --cov-report=term-missing
```

## 3. Frontend (React + TypeScript, Jest + RTL)

| Тип | Расположение | Команда |
|-----|--------------|---------|
| Утилиты | `src/utils/__tests__/` | `npm run test:ci` |
| Компоненты / сценарии | `src/components/**/__tests__/`, `App.test.tsx` | то же |
| Покрытие | — | `npm run test:coverage` |

**Важно:** в проекте не должно быть «чужого» `@testing-library/react` v16+ только в корневом `node_modules` при React 18 — Jest поднимет его раньше локального и выдаст ошибку про «старый React». Зависимости тестов объявлены в `frontend/package.json` (`@testing-library/react` ^14).

## 4. E2E (Playwright)

- Конфиг: `frontend/playwright.config.ts`
- Сценарии: `frontend/e2e/*.spec.ts`
- Команда (из `frontend`): `npx playwright install chromium` (один раз после `npm install`), затем `npm run test:e2e` (в `package.json` включён репортер `list` — по строке на каждый сценарий)
- Если при первом запуске ошибка **`Executable doesn't exist` … `chromium_headless_shell`**: выполните ту же команду `npx playwright install chromium` из каталога `frontend` (скачиваются браузеры в `%LOCALAPPDATA%\ms-playwright`, в репозиторий они не входят).

Переменные:

- `PLAYWRIGHT_SKIP_WEBSERVER=1` — не поднимать dev-server (если уже запущен `npm start`).
- `E2E_ADMIN_USER` / `E2E_ADMIN_PASSWORD` — для сценария входа/выхода (иначе тест помечается как пропущенный).

Нужны одновременно backend (`127.0.0.1:8001`) и фронт (`127.0.0.1:3000` или `PLAYWRIGHT_BASE_URL`).

## 5. Инфраструктура

- Отдельное тестовое окружение backend через `APP_ENV=test` и изолированная БД.
- Моки внешних вызовов в интеграционных тестах (погода и т.д.).
- Сброс состояния: pytest-фикстуры и транзакции/пересоздание таблиц по мере необходимости; Jest `resetMocks: true` (CRA).

---

## 6. Метрики качества

- **Backend / frontend:** минимальные пороги покрытия на фронте заданы в `package.json` → `jest.coverageThreshold` (порог веток 9%, остальное 10% — стартовая планка для роста).
- **Слои:** маркеры pytest `unit` / `integration` / `slow`; unit/integration — быстрые; e2e — отдельный прогон.
- **Именование:** `test_*.py` в backend; `*.test.ts(x)` и каталоги `__tests__` на фронте; e2e — `*.spec.ts`.

---

## 7. Итоговая проверка (чек-лист)

1. `cd backend && pytest tests` — зелёный прогон.
2. `cd frontend && npm run test:ci` — зелёный прогон.
3. При необходимости отчёта по покрытию фронта: `npm run test:coverage`.
4. E2E: backend + frontend запущены, затем `npm run test:e2e` в `frontend`.
5. Ручная сверка: гость не видит админские пункты; с неверным паролем вход невозможен (дублируется тестами API и e2e при заданных переменных).
